# Memoh 智能客服实施路线与数据设计

> 目标：在尽量不做破坏性升级的前提下，把智能客服作为 Memoh 的业务域逐步落地。

## 1. 实施总原则

1. **先配置化，后平台化**
   - 第一阶段优先通过 department、bot metadata、skill、MCP 授权、prompt 编排实现闭环。
   - 不急于一开始就引入复杂新表和规则引擎。
2. **先跑通单条业务链路，再扩产品线**
   - 先选一个产品线做试点。
3. **先保证可控，再追求自动化率**
   - 早期优先保证路由正确、权限正确、可转人工。
4. **人工协同能力必须同步建设**
   - 智能客服不是纯 bot 项目，必须同时考虑接管、工单、SLA、上下文摘要。

## 2. 三阶段实施路线

### 2.1 Phase 1：试点可跑通阶段

**目标：** 跑通从客户消息进入，到 AI 路由，再到专业 bot 响应或转人工的最小闭环。

**建议范围：**

- 先接入 1 个外部渠道，例如 Web Chat 或 Telegram
- 先覆盖 1 个主要产品线
- 先覆盖两类高频问题：
  - 售前咨询
  - 售后查询 / 基础问题

**本阶段建议建设内容：**

1. 建立“智能客服部”
2. 建立前台路由 bot、售前 bot、售后 bot、产品专家 bot
3. 为不同 bot 配置不同 skill 模板
4. 为不同 bot 配置不同 MCP 权限
5. 在 bot metadata 中增加客服域标记
6. 用 subagent 实现内部委派
7. 先通过配置和 prompt 路由，避免过早做规则引擎
8. 定义最基本的人工接管规则
9. 为前台路由 bot 增加情绪识别与安抚策略

**建议交付物：**

- 客服域 bot 清单
- 客服域 skill 模板清单
- 客服域 MCP 权限矩阵
- 前台路由 prompt / routing 策略
- 情绪识别与安抚话术策略
- 高情绪风险转人工规则
- 优秀安抚话术沉淀机制
- 试点产品知识库与 FAQ
- 人工接管操作说明
- 基础监控面板

**验收标准：**

- 外部渠道消息可进入 Memoh
- 系统可识别主要语言并输出对应语言回复
- 系统可在售前 / 售后 / 产品线之间完成基本分流
- 系统可识别高情绪风险并执行安抚或转人工
- 专业 bot 只能访问允许的工具
- 无法处理的问题可明确转人工
- 关键过程可审计、可回溯

### 2.2 Phase 2：业务成型阶段

**目标：** 把试点能力沉淀成客服域的一等能力。

**建议建设内容：**

- 服务队列模型
- 路由规则模型
- 情绪状态与安抚效果评估模型
- 转人工状态机
- 工单模型
- 会话优先级与 SLA
- 升级处理机制
- 客服质检报表
- 坐席工作台 / Copilot

**建议新增平台能力：**

1. 服务队列
2. 显式路由规则
3. 人工接管闭环
4. 工单化管理
5. 安抚效果沉淀与复用
6. 坐席辅助 Copilot

**验收标准：**

- 新产品线接入时不需要重写整套 prompt
- 路由决策可配置、可解释、可审计
- 情绪识别结果、安抚尝试过程、转人工决策可追踪
- 人工接管全链路有状态、有记录
- 跨团队协作问题可通过 ticket 持续跟踪
- 坐席接手时能看到 AI 总结和上下文

### 2.3 Phase 3：规模化运营阶段

**目标：** 面向多地区、多产品、多语言和更高运营要求持续优化。

**建议建设内容：**

- 更完整的多语言知识库体系
- 区域化模型策略
- 情绪识别精细化与安抚策略优化
- 自动回访 / 定时跟进
- 复杂运营报表
- KPI 与 AI 辅助效果量化
- 高价值客户 / 高风险会话识别
- 更细粒度的权限与合规控制

**验收标准：**

- 新语言、新地区接入成本明显下降
- 高价值场景有清晰 SLA 与升级机制
- 运营团队可持续衡量 AI 客服效果
- 合规和权限问题能被快速发现和追踪

## 3. 建议实施顺序

1. 组织建模
2. 权限建模
3. 试点产品接入
4. 路由 bot 上线
5. 专业 bot 上线
6. 人工接管上线
7. 数据化运营

## 4. 项目角色建议

建议至少明确：

- 业务负责人：定义售前 / 售后流程、升级规则、服务边界
- 知识库负责人：维护 FAQ、SOP、产品资料、多语言内容
- 系统集成人员：梳理 CRM、订单、设备、计费等系统接入
- 平台研发人员：负责 bot、MCP、权限、路由、工单等实现
- 运营 / 质检人员：验证质量、标注问题案例、持续优化规则

## 5. 推荐里程碑

- **Milestone A**：完成试点上线
- **Milestone B**：完成人工接管闭环
- **Milestone C**：完成客服域平台化
- **Milestone D**：完成多区域规模化运营

## 6. 第一阶段建议的数据建模策略

当前不建议一开始就把客服域硬编码进核心 schema，优先用 metadata 承载业务域属性。

### 6.1 bot metadata 建议字段

```json
{
  "domain": "customer_service",
  "service_type": "presales",
  "product_line": "global_wifi",
  "service_queue": "presales-global-wifi",
  "region_scope": ["global"],
  "languages": ["zh", "en", "ja", "es"],
  "human_handoff_enabled": true,
  "emotion_policy": {
    "enabled": true,
    "max_deescalation_turns": 2,
    "handoff_on_high_risk": true
  }
}
```

### 6.2 第二阶段建议新增的正式模型

后续可新增：

- `service_queues`
- `queue_members`
- `queue_bot_bindings`
- `conversation_handoffs`
- `tickets`
- `ticket_events`
- `routing_rules`
- `customer_profiles`
- `conversation_labels`
- `conversation_emotion_states`
- `deescalation_attempts`
- `deescalation_playbooks`

### 6.3 为什么第一阶段先用 metadata

因为当前平台已经具备：

- bots
- departments
- settings
- RBAC
- MCP capability

这样做的好处是：

- 降低 schema 变更范围
- 快速验证组织模型是否合理
- 避免过早把客服域写死进通用平台核心结构

## 7. 当前接口能力映射

当前 agent gateway 已提供：

- `/chat`
- `/chat/stream`
- `/chat/trigger-schedule`
- `/chat/trigger-heartbeat`
- `/chat/subagent`

因此第一阶段不需要先新增独立客服执行接口，就已经可以承载：

- 客户发起咨询
- AI 流式回复
- specialist bot 委派
- 定时回访 / 跟进
- heartbeat 巡检与主动触达

### 7.1 关键挂载点

当前服务端已有两个很重要的策略挂载点：

1. **Chat Pre Check**
   - 适合扩展黑名单、风险会话拦截、必须转人工预判等前置策略。
2. **Model Override**
   - 适合根据语言、复杂度、客户等级、成本约束做模型覆盖。

### 7.2 enterprise 能力映射

现有 enterprise 能力对客服域的价值：

- Department：组织归属
- Audit：关键操作审计
- Cockpit：运营报表基础
- Hands：运营动作 / 批量跟进 / 调度
- Model Routing：复杂度 / 成本 / 场景路由
- Cost Tracking / Budget：预算与成本治理

## 8. 第一阶段建议补充的上下文字段

第一阶段建议优先把字段放进 metadata、context 或渠道适配层入参，而不是做破坏性接口改造。

### 8.1 会话入口请求侧

建议补充：

- `channel_type`
- `external_conversation_id`
- `external_thread_id`
- `customer_id`
- `customer_tier`
- `service_domain`
- `service_type_hint`
- `product_line_hint`

### 8.2 客服上下文扩展

建议补充：

- `language_hint`
- `region_hint`
- `emotion_hint`
- `required_capability`
- `handoff_policy`
- `sla_policy`
- `service_queue`

### 8.3 输出侧建议字段

建议在响应或 `agent_end.messages[].metadata.customer_service` 中承载：

- `trace_id`
- `resolved_queue`
- `resolved_product_line`
- `handoff_decision`
- `handoff_reason`
- `emotion_assessment`
- `deescalation_result`
- `ticket_status`
- `sla_deadline_at`

## 9. 当前数据模型映射

### 9.1 bots

建议用 `bots.metadata` 承载：

- `domain=customer_service`
- `service_type=presales|aftersales`
- `product_line=xxx`
- `human_handoff_enabled=true`
- `languages=[...]`
- `emotion_policy={...}`

### 9.2 departments / department_members / bot_department_access

建议用来承载：

- 智能客服部
- 售前 / 售后 / 产品服务小组
- 客服主管 / 坐席成员
- bot 的组织归属和治理边界

### 9.3 bot_permissions + MCP connections

建议用来承载：

- 售前 bot 只能访问 FAQ / 产品知识 / CRM
- 售后 bot 可访问订单 / 退款 / 工单
- 不同产品 bot 的系统边界隔离
- 外部客服 bot 不得访问管理类工具

### 9.4 bot_channel_routes + bot_history_messages

建议用来承载：

- 外部客户会话与 bot 的绑定关系
- 渠道会话 ID / 线程 ID
- 默认回复目标
- 会话历史消息
- 情绪等级 / 安抚结果 / 是否升级等 metadata

### 9.5 情绪状态与安抚记录

第一阶段建议先放 metadata，例如：

- `emotion_level`
- `emotion_tags`
- `handoff_reason=emotion_risk`
- `deescalation_attempt_count`
- `deescalation_result=calmed|unchanged|escalated`

### 9.6 bot_inbox

可先承载：

- 未立即处理的消息
- 待人工回看事项
- 跟进提醒 / 异步通知
- 搜索历史待办

### 9.7 subagents

适合承载：

- 语言专家协作
- 产品专家协作
- 售后诊断协作
- 翻译 / 本地化协作

### 9.8 bot_model_routes / budgets / audit_logs

适合承载：

- 多语言或复杂场景的模型路由
- 成本控制
- 审计和运营治理

## 10. 第一阶段最关键的边界

第一阶段最重要的不是把客服域抽象得多完整，而是保证：

- 能接入外部客户消息
- 能正确分流
- 权限边界可控
- 情绪高风险能及时转人工
- 会话、人工接管、后续跟进有最基本的数据留痕
