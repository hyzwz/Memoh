# Memoh 智能客服开发蓝图

> 目标：把现有“智能客服方案”系列文档补齐为可指导研发实施的开发蓝图，并作为后续 Phase 1 开发的直接输入。

---

## 1. 文档定位

本文件不是重复描述“为什么做智能客服”，而是回答以下问题：

- 基于当前 Memoh 代码结构，客服域能力具体挂到哪里
- 哪些能力 Phase 1 先配置化落地，哪些能力进入 Phase 2 平台化
- 后端、Agent、前端分别要新增什么模块
- 哪些数据继续复用现有表，哪些数据先放 metadata，哪些数据应升级为正式模型
- 开发顺序、接口边界、验收口径如何定义

建议与以下文档配合阅读：

- `docs/architecture/智能客服方案总览.md`
- `docs/architecture/智能客服系统架构方案.md`
- `docs/architecture/智能客服实施路线与数据设计.md`
- `docs/architecture/智能客服前端状态机与工作台设计.md`

## 2. 总体开发结论

智能客服应作为 Memoh 平台中的一个业务域扩展，而不是一个平行新系统。

开发上的基本判断如下：

1. **Phase 1 不以大规模 schema 改造为前提**
   - 优先复用现有 `bots`、`departments`、`bot_channel_routes`、`bot_history_messages`、`subagents`、`bot_inbox`、`settings`、`RBAC`、`MCP`。
   - 客服域属性优先放在 bot metadata、会话 context、流式消息 metadata 中。

2. **Phase 1 先打通“可控闭环”**
   - 目标不是最高自动化率，而是先让客服链路具备可分流、可转人工、可审计、可限权。

3. **Phase 2 再把客服域平台化**
   - 进入正式模型：queue、handoff、ticket、routing rule、emotion state、playbook、SLA。

4. **前台 bot 是编排入口，不是唯一执行者**
   - 对外统一入口，对内委派 specialist bot / subagent。

5. **人工协同从第一天开始纳入设计**
   - “转人工”不是异常兜底，而是客服域主流程的一部分。

## 3. 当前代码能力映射

基于当前仓库结构，客服域开发应优先建立在以下模块之上。

### 3.1 Go Server

主要挂载点：

- `internal/channel/`

  - 异步待处理事项

- `internal/rbac/`
  - bot 与 department 的访问控制
- `internal/handlers/`

- `internal/mcp/providers/`
  - CRM、订单、知识库、消息发送、subagent 等工具边界

### 3.2 Agent Gateway 与 Agent Core

主要挂载点：

- `apps/agent/src/modules/chat.ts`

- `packages/agent/src/agent.ts`
  - 主对话流与子 Agent 调用
- `packages/agent/src/prompts/`

### 3.3 Web 前端

- `apps/web/src/router.ts`

- `apps/web/src/pages/enterprise/`
  - department / cockpit 等现有治理能力复用

## 4. 开发范围分层

### 4.1 Phase 1：试点闭环

必须具备：

- 1 个外部渠道接入
- 1 个前台路由 bot
- 至少 2 个 specialist bot：售前、售后
- 基于 metadata / prompt 的语言识别、问题分类、产品线识别
- 高情绪风险识别与有限轮次安抚
- 明确的转人工决策
- bot 工具权限边界
- 流式消息 metadata 承载客服态信息
- 最小客服工作台视图

### 4.2 Phase 2：平台化

新增正式域模型：

- service queue
- handoff
- ticket
- routing rule
- conversation label
- emotion state
- deescalation playbook
- SLA / priority

### 4.3 Phase 3：规模化运营

增强能力：

- 多区域与多语言策略
- 区域化模型路由
- 更精细的风控、情绪识别、升级策略
- 定时回访与自动跟进
- 运营报表、质检、ROI 分析

## 5. 客服域模块拆分

推荐把客服域开发拆成六个子域，避免把逻辑散落在已有通用模块中。

### 5.1 Inbound Enrichment

职责：

- 从渠道入站消息中补充客服域上下文
- 统一抽取 `channel_type`、`external_conversation_id`、`customer_id`、`product_line_hint`
- 识别这是普通 bot 对话还是客服域会话

建议挂载点：

- `internal/channel/`
- `internal/conversation/flow/`

Phase 1 形态：

- 以请求上下文 enrichment 为主
- 不要求先新增数据库表

### 5.2 Customer Service Orchestration

职责：

- 在前台路由 bot 外围做客服域编排
- 管理分类、委派、转人工、人工优先策略
- 规范输出 `customer_service` metadata

建议挂载点：

- `internal/conversation/flow/`
- 如逻辑增多，可新增 `internal/customerservice/` 包

Phase 1 形态：

- 先做轻量 orchestrator
- 主要负责上下文组装、前后置策略、结果规范化

### 5.3 Specialist Execution

职责：

- 售前、售后、产品专家 bot 的能力执行
- 根据 bot metadata 与 MCP 授权做系统访问隔离

建议挂载点：

- `packages/agent/src/prompts/`
- `internal/mcp/providers/`
- `internal/subagent/`

Phase 1 形态：

- 优先复用已有 subagent 机制
- 专业 bot 先通过 bot 配置和 skill 模板组织，不要求新服务

### 5.4 Human Collaboration

职责：

- 记录接管决策
- 将会话切换到人工处理态
- 为坐席提供摘要、建议回复、上下文检索

建议挂载点：

- 后端：`internal/handlers/`、`internal/inbox/`
- 前端：客服工作台页

Phase 1 形态：

- 先做到“可触发接管、可看到待接管会话、可标记已接手”
- ticket/SLA 可留到 Phase 2

### 5.5 Governance & Audit

职责：

- 客服 bot 与部门绑定
- 审计关键操作
- 监控模型成本与高风险会话

建议挂载点：

- `internal/enterprise/`
- `internal/rbac/`
- `internal/handlers/audit_*`

### 5.6 Operator UI

职责：

- 客服工作台
- 会话详情
- 人工接管与回切
- 状态可视化

建议挂载点：

- `apps/web/src/pages/customer-service/`

## 6. Phase 1 推荐后端结构

为避免客服逻辑散落，建议在 Go 侧引入一个明确但轻量的业务包：

```text
internal/customerservice/
  types.go           # DTO / metadata / enum / policy
  context.go         # 请求上下文 enrichment
  orchestrator.go    # 前后置客服策略
  router.go          # 分类与委派决策包装
  handoff.go         # 转人工决策与最小状态流
  emotion.go         # 情绪识别结果与安抚策略包装
  audit.go           # 客服域审计辅助
```

设计原则：

- **不替代** `internal/conversation/flow/`，而是嵌入其前后置流程
- **不封装 LLM 本体**，仅负责客服域上下文和策略
- **不直接侵入每个 channel adapter**，尽量在入站归一化后处理

- `bot_inbox`
- `subagents`

- 不为“可能以后需要”提前建表

## 8. Phase 1 核心接口与事件契约

### 8.1 继续复用的执行接口

Phase 1 原则上继续复用：

- `POST /chat`
- `POST /chat/stream`
- `POST /chat/subagent`

原因：

- 现有 Agent Gateway 已可承担主对话、流式响应和 specialist bot 委派
- 先避免单独再发明一套客服执行接口

### 8.2 建议新增的服务端接口

建议先新增最小客服域 API，用于工作台和人工协同，而不是替换 chat 接口。

```text
GET    /customer-service/conversations
GET    /customer-service/conversations/{id}
POST   /customer-service/conversations/{id}/handoff
POST   /customer-service/conversations/{id}/claim
POST   /customer-service/conversations/{id}/release
POST   /customer-service/conversations/{id}/resume-ai
GET    /customer-service/inbox
GET    /customer-service/queues             # Phase 2 可正式化
```

Phase 1 也可以先只实现以下最小集合：

```text
GET    /customer-service/conversations
GET    /customer-service/conversations/{id}
POST   /customer-service/conversations/{id}/handoff
POST   /customer-service/conversations/{id}/claim
```

### 8.3 会话详情响应建议

```json
{
  "id": "conv-001",
  "channel_type": "telegram",
  "customer_id": "cust-001",
  "customer_tier": "vip",
  "assigned_bot_id": "front-desk-bot",
  "assigned_human_id": "user-123",
  "phase": "handoff_active",
  "service_type": "after_sales",
  "product_line": "global_wifi",
  "emotion_level": "high",
  "handoff_reason": "high_emotion_risk",
  "last_message_at": "2026-03-24T10:00:00Z",
  "summary": "用户投诉设备无法联网，已安抚 1 轮，建议人工接手。",
  "messages": []
}
```

### 8.4 流式事件扩展约定

在不破坏现有 SSE 协议的前提下，约定 `agent_end` 或相关消息 metadata 包含客服域字段。

前端至少要能识别：

- `handoff_decision`
- `handoff_reason`
- `emotion_assessment.level`
- `deescalation_attempts`
- `specialist_bot`

如果后续需要更强实时性，再考虑显式新增事件：

- `customer_service.classified`
- `customer_service.handoff_requested`
- `customer_service.handoff_confirmed`

Phase 1 不强依赖新增事件名，优先复用 metadata。

## 9. 路由与委派策略

### 9.1 前台路由 bot 的职责边界

只负责：

- 识别语言
- 识别问题类型
- 识别产品线
- 识别情绪等级
- 决定直答、委派、转人工

不负责：

- 深度业务系统操作
- 跨多个 specialist bot 的长链路自由讨论

### 9.2 specialist bot 的职责边界

售前 bot：

- FAQ
- 产品介绍
- 购买咨询
- 套餐说明

售后 bot：

- 查询类问题
- 常见售后诊断
- 订单 / 退款 / 履约状态解释

产品专家 bot：

- 某产品线的专业知识与工具调用

### 9.3 推荐委派路径

```text
客户消息
  -> 前台路由 bot
    -> 分类与风险判断
    -> specialist bot / subagent
    -> 输出回复或 handoff 决策
  -> 人工坐席接管
    -> Copilot 生成摘要、建议回复、系统聚合信息
```

## 10. 人工协同最小状态机

Phase 1 后端建议至少定义以下会话处理态：

- `ai_active`
- `awaiting_handoff`
- `handoff_active`
- `human_resolved`
- `ai_resumable`

状态变更规则：

1. `ai_active`
   - 默认状态，AI 正常处理
2. `awaiting_handoff`
   - AI 已建议转人工，等待接管
3. `handoff_active`
   - 某人工坐席已接手，AI 不再自动继续
4. `human_resolved`
   - 人工已处理完成
5. `ai_resumable`
   - 允许 AI 继续跟进，但应有明确触发动作

Phase 1 可以先把这套状态存储在 conversation metadata 或 handoff 记录中；Phase 2 再升级为正式 handoff / ticket 模型。

## 11. 权限与工具隔离策略

### 11.1 bot 权限隔离

客服域必须坚持：

- 一个 specialist bot 只访问本产品线工具
- 前台 bot 不直接拥有所有后台系统的高权限工具
- Copilot 可读信息可多于前台 bot，但写操作必须收紧

### 11.2 department 绑定建议

建议至少创建：

- 智能客服部
- 售前服务组
- 售后服务组
- 产品 A / B 服务组

bot 与 department 关系：

- 前台路由 bot 可归属“智能客服部”
- specialist bot 分别归属对应服务组
- 人工坐席只看自己有权限的服务组会话

### 11.3 审计重点

必须记录：

- 转人工决策
- 人工 claim / release
- specialist bot 委派
- 关键工具调用
- 高风险情绪会话
- 恢复 AI 处理

## 12. 前端开发蓝图

### 12.1 页面拆分建议

```text
apps/web/src/pages/customer-service/
  index.vue                     # 工作台首页
  conversations/index.vue       # 会话列表
  conversations/detail.vue      # 会话详情
  handoffs/index.vue            # 待接管列表
  settings/index.vue            # 客服域配置（后期）
```

### 12.2 Phase 1 工作台最小能力

- 会话列表
- 当前状态筛选
- 风险级别标识
- 查看 AI 摘要
- 查看完整消息流
- 手动接管按钮
- 接管中状态提示

### 12.3 前端状态管理原则

- 会话级状态和消息级状态分离
- SSE 事件先归一化，再进入 reducer
- 客服态字段集中映射到 `customer_service` 视图模型
- “转人工中”和“普通回复完成”必须是不同 UI 状态

详细状态机可继续沿用：

- `docs/architecture/智能客服前端状态机与工作台设计.md`

## 13. Phase 1 开发顺序

推荐严格按以下顺序推进，避免前后端空转。

### 13.1 第一步：组织与 bot 建模

- 创建客服部门结构
- 约定 bot metadata 字段
- 准备前台 bot / specialist bot / Copilot bot 清单
- 明确 MCP 权限矩阵

### 13.2 第二步：后端上下文与 metadata 链路

- 入站消息补齐客服上下文
- 在 `conversation/flow` 中接入客服 orchestrator
- 规范 `customer_service` metadata 输出

### 13.3 第三步：委派与风控闭环

- 路由 bot 可以委派 specialist bot
- 高情绪风险可以触发 handoff 决策
- 关键决策有 audit 记录

### 13.4 第四步：最小人工协同接口

- 会话列表 API
- 会话详情 API
- handoff / claim API

### 13.5 第五步：客服工作台

- 列表页
- 详情页
- 接管动作
- 状态展示

### 13.6 第六步：验证与试点上线

- 试点渠道
- 试点产品线
- 高风险案例回放
- 权限与审计复核

## 14. 测试与验收蓝图

### 14.1 后端测试

优先补充：

- `conversation/flow` 的客服 metadata 输出测试
- handoff 决策测试
- specialist bot 委派链路测试
- RBAC 下的工具隔离测试
- 客服域 handler 测试

### 14.2 Agent 测试

优先补充：

- 前台 bot prompt 输出结构化字段的契约测试
- specialist bot 委派行为测试
- 高情绪风险场景样例测试

### 14.3 前端测试

优先补充：

- SSE 事件 reducer 测试
- handoff UI 状态切换测试
- 会话详情视图模型测试

### 14.4 Phase 1 验收标准

- 客户消息可从外部渠道进入并绑定到客服域 bot
- 前台 bot 能区分售前 / 售后 / 产品线
- specialist bot 权限边界正确
- 高情绪风险能触发安抚或转人工
- 人工可看到待接管会话并成功 claim
- 会话关键过程可回溯、可审计

## 15. Phase 2 进入条件

当出现以下信号时，说明应从“配置化试点”进入“正式平台化”：

- 新产品线接入已频繁复制 prompt 和 bot 配置
- 转人工逻辑开始出现跨团队协同与 SLA 需求
- 需要按队列统计效率与质量
- metadata 已无法支撑筛选、报表、回放与审计
- 客服运营方要求可配置化 routing rule 和 playbook

此时应正式进入：

- queue 模型
- handoff 模型
- ticket 模型
- emotion / deescalation 模型
- 坐席工作台平台化

---

## 16. 建议的首个开发包边界

如果文档评审通过，建议开发从以下最小包开始：

1. `internal/customerservice/`
   - 定义 Phase 1 类型、metadata 结构和 handoff 决策辅助
2. `internal/conversation/flow/`
   - 接入客服上下文 enrichment 与 metadata 输出
3. `internal/handlers/`
   - 提供最小客服工作台 API
4. `apps/web/src/pages/customer-service/`
   - 建立工作台骨架与会话详情页

换句话说，第一轮开发不应从“复杂表设计”开始，而应从“客服上下文链路 + handoff 最小闭环 + 工作台最小视图”开始。
