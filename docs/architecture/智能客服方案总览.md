# Memoh 智能客服方案总览

> 目标：把智能客服作为 Memoh 平台中的一个业务域扩展，而不是新建一套割裂的独立系统。

## 1. 结论

当前阶段不建议为途鸽公司的全球化、多语言智能客服需求单独再开发一个新项目。

更合适的方向是：

- 继续基于 Memoh 现有底座扩展客服域能力
- 让内部助理与外部智能客服共用同一平台底座
- 用 department、bot、skill、MCP、subagent、RBAC、audit、model routing、cost tracking 去承载客服场景

核心判断：

> 约 1000 会话/天 的规模，对当前项目来说主要矛盾不是极限吞吐，而是业务分流、权限隔离、系统接入、人工协同与运营治理。

## 2. 为什么不建议拆成两套系统

如果把平台拆成“内部助理系统”和“外部客服系统”，会带来几个明显问题：

- bot 能力和工具配置重复建设
- 模型、权限、审计、监控体系分裂
- 后续人工客服 Copilot 与内部系统协同更难统一
- 多语言、知识库、运营规则会重复维护

因此更推荐的目标是：

> 一个统一 AI 平台，同时承载内部助手与外部客服两类场景。

## 3. 业务目标

途鸽客服场景的关键特征：

- 客户全球分布，语言种类多
- 客服按售前、售后两大类组织
- 每个大类下再按产品线细分
- 不同产品线需要访问不同内部系统
- 当前人工流程本质上是“识别问题 → 判断产品/类型 → 路由给合适人员处理”

因此平台不仅要能聊天，还要具备：

- 多语言识别与处理
- 问题分类
- 产品识别
- 情绪识别与安抚
- 路由分发
- 专业 bot 协作
- 人工接管
- 企业系统工具隔离

## 4. 设计原则

1. **统一平台，不做双系统割裂**
   - 内部助理和外部客服共用同一套平台基础设施。
2. **组织归属与业务路由分离**
   - department 负责归属、权限、模板管理。
   - queue / service unit 负责业务分流。
3. **工具权限按 bot 隔离**
   - 不同产品客服 bot 只能访问对应系统。
4. **优先委派，不优先 bot 互聊**
   - 用前台 bot + specialist bot / subagent 的方式组织协作。
5. **人工客服是一等角色**
   - 系统必须支持转人工、接管、工单、SLA、Copilot。

## 5. 当前 Memoh 可直接复用的能力

### 5.1 bot 运行时隔离

- 每个 bot 独立容器运行
- MCP 能力按 bot 隔离
- 适合区分内部助理 bot 与客服 bot

### 5.2 skill 系统

- 可为售前、售后、产品专家 bot 配不同技能模板
- 适合把客服 SOP、话术策略、流程能力挂到 bot 上

### 5.3 MCP 工具体系

- 可按产品线接入 CRM、订单、设备、计费、知识库等系统
- 天然适合做“不同客服 bot 的不同系统访问边界”

### 5.4 department 能力

现有 enterprise 扩展已具备：

- 部门
- 部门成员
- bot 对部门的访问授权
- 部门技能模板
- RBAC 能力

这意味着“智能客服部”完全可以成为正式组织单元。

### 5.5 subagent 机制

适合承载：

- 语言识别 / 翻译
- 产品识别
- 售后诊断
- 专业知识问答

### 5.6 历史消息 / inbox / channel routes

适合承载：

- 客服消息轨迹
- 渠道会话绑定关系
- 异步待处理事项
- 后续审计与检索

## 6. 客服组织模型

推荐按三层组织：

### 6.1 组织层：department

例如：

- 智能客服部
- 售前服务组
- 售后服务组
- 产品 A 服务组
- 产品 B 服务组

### 6.2 业务层：queue / service unit

例如：

- 售前队列
- 售后队列
- 产品 A 队列
- 产品 B 队列
- VIP 队列

### 6.3 执行层：角色 bot

例如：

- 前台路由 bot
- 售前专家 bot
- 售后专家 bot
- 产品专家 bot
- 人工坐席 Copilot bot

一句话总结：

> department 负责组织归属，queue 负责业务路由，bot 负责执行能力，MCP / skill 负责权限边界。

## 7. 推荐的 bot 协作模型

不建议让多个 bot 长链路互聊。

更合适的方式是：

- 客户只面对一个前台客服 bot
- 前台客服 bot 内部委派给 specialist bot / subagent
- 无法处理时转人工
- 人工坐席旁边挂一个 Copilot bot

推荐协作链路：

```text
客户
  -> 前台路由 bot
    -> 语言识别 / 情绪识别 / 产品识别
    -> 委派售前 / 售后 / 产品专家 bot
    -> 直接回复 或 决定转人工
  -> 人工坐席接管
    -> Copilot 提供摘要、建议回复、检索结果
```

## 8. 客服角色建议

### 8.1 前台路由 Bot

职责：

- 判断语言
- 判断问题类型
- 判断产品归属
- 判断情绪风险
- 决定分流、委派或转人工

### 8.2 售前 / 售后 / 产品专家 Bot

职责：

- 使用各自权限范围内的 MCP 工具处理问题
- 回复客户或输出给前台 bot 的结构化结果
- 在无法闭环时触发人工接管建议

### 8.3 人工坐席 Copilot Bot

职责：

- 为人工坐席生成摘要
- 产出建议回复
- 聚合知识库 / CRM / 订单 / 系统信息
- 帮助人工提升处理效率，而不是替代人工责任

## 9. 情绪识别与安抚策略

在客服场景中，情绪识别不是可选增强，而是核心策略能力。

建议前台路由 bot 具备：

- 识别激动、不满、焦虑、投诉升级等情绪状态
- 在高风险情绪下优先使用更稳妥的安抚话术
- 限制安抚轮次，避免 AI 与高情绪客户长时间对话失控
- 如果安抚失败或风险持续升高，立即转人工

同时应记录：

- 当前情绪等级
- 情绪标签
- 安抚尝试次数
- 安抚结果是缓和、持平还是升级
- 哪些成功话术值得后续沉淀复用

## 10. 总体架构

完整架构主张如下：

- 外部渠道统一接入 Inbound Processor
- 渠道会话通过 `bot_channel_routes` 与 bot 绑定
- 前台客服 bot 负责理解、分流、安抚和决策
- specialist bot 通过 subagent 模式协作
- MCP 层承载 CRM、订单、设备、知识库、计费等系统接入
- Enterprise 层承载 department、audit、cockpit、hands、model routing、cost tracking
- 人工协同层承载坐席工作台、工单、接管与升级

## 11. 建议的第一阶段边界

第一阶段重点不是把客服域做成完整平台，而是先跑通最小业务闭环：

- 接入 1 个外部渠道
- 覆盖 1 个产品线
- 跑通售前、售后两类高频场景
- 落地前台路由 + specialist bot + 转人工
- 补齐情绪识别与安抚策略
- 确保 bot 权限和 MCP 边界可控
